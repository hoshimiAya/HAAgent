# 提交规范（AI 主导）

本文件主要供 AI 读取，用于分析 git diff 并生成规范 commit message 与提交命令。
人类读者只需了解结构，不必记规则。

---

## 0. 调用方式

用户提供：
- `git diff --staged` 或 `git diff HEAD` 的输出
- 可选：本次变更的背景说明

AI 输出：
- 若变更应拆分为多个 commit，先给出拆分建议（见 §5）
- 否则直接给出 commit message（见 §1.1）
- 无论是否拆分，都附带可直接执行的 `git add` / `git commit` 命令（见 §1.2）

---

## 1. 输出内容（硬约束）

每次回复必须包含两部分：commit message 与提交命令。
若触发拆分（§5），则为每个 commit 各给一组。

### 1.1 commit message 格式

    <type>: <简述>

    [可选正文]

- 首行 ≤ 30 字符，无句号，动词或名词短语开头
- 第二行为空行（若有正文）
- 正文用中文，说"为什么"，不复述"做了什么"
- 无正文时只有一行

### 1.2 提交命令格式

每条命令单行，跨 bash / PowerShell / cmd 通用。

单行 message：

    git add "<文件>"
    git commit -m "<标题>"

带正文（每个 `-m` 一个段落，Git 自动在相邻 `-m` 间插入空行）：

    git add "<文件1>" "<文件2>"
    git commit -m "<标题>" -m "<正文段1>" -m "<正文段2>"

规则：

- 第一个 `-m` 是标题，其余是正文段
- 正文每个自然段对应一个 `-m`，段内不再换行
- 路径一律双引号包裹，兼容中文文件名与空格
- 文件清单从 diff 的 `diff --git a/X b/X` 行提取，取 `b/` 后的路径
- 只 add 该 commit 涉及的文件，禁止 `git add -A` / `git add .`
- message 含双引号时，把该 `-m` 参数改用单引号包裹
- 多个 commit 时，各组 add/commit 互相独立，用户按顺序粘贴执行

不要用 heredoc（`<<'EOF'`）：那是 bash 专有语法，PowerShell 会报
`The '<' operator is reserved`，且 heredoc 内的多行内容会被当成独立命令
逐行执行。多个 `-m` 在所有 shell 下行为一致，且每条命令单行，粘贴零风险。

## 2. type 决策表（按 diff 内容判断）

| diff 特征 | type |
|-----------|------|
| 新增函数 / 类 / 路由 / 接口 | `feat` |
| 修复可复现的错误行为 | `fix` |
| 改结构、不改外部行为（重命名、抽函数、换实现） | `refactor` |
| 仅改注释、文档、README、docs/ | `docs` |
| 构建脚本、依赖、配置文件、CI | `chore` |
| 仅改空白、缩进、格式化 | `style` |
| 新增/修改测试 | `test` |
| 性能优化，且行为不变 | `perf` |

**多特征时优先级**：`fix` > `feat` > `refactor` > `perf` > `test` > `docs` > `chore` > `style`

若 diff 同时含多个不相关特征 → 触发 §5 拆分。

---

## 3. 标题生成规则

提取：
1. diff 中**新增/删除最多的符号**所在模块
2. 该模块下**最核心的行为变化**

措辞模板：
- 新增：`添加 X` / `实现 X` / `接入 X`
- 删除：`移除 X` / `删除 X`
- 修改：`X 改为 Y` / `调整 X`
- 修复：`修复 X` / `解决 X 导致的 Y`

**禁用词**（无信息量）：
`更新` `修改` `提交` `调整一下` `小改` `fix` `bug fix` `WIP`

**推荐长度**：15–25 字符，能把"哪个模块做了什么"说清。

---

## 4. 正文生成规则

**默认不写正文。** 只有满足下列任一条件才写：

- 修复的 bug 根因不在表面（需解释"为什么这么改"）
- 涉及破坏性变更（API、配置、数据格式）
- 有一次取舍（选了方案 A，放弃了 B）
- 引入新的外部依赖或约束

**不写正文**：新增独立文件、重命名、单纯补文档、加个 handler、一眼能看出根因的修复。

正文格式：
- 中文，短句，无标点堆砌
- **正文总量 ≤ 2 句、≤ 60 字**，超出说明在复述 diff
- 正文优先单段；确需分段时按语义拆成 2 段以内，每段对应命令里的一个 `-m`，段内不换行
- 不要列表符号，直接自然段

---

## 5. 拆分规则

一个 commit 只做一件事。判断标准：

**必须拆分**：
- 同时有 `feat` 和 `fix`
- 同时改 src/ 和 docs/（除非文档是代码的必附说明）
- 同时改多个独立模块（如 `llm/` 和 `routing/`）

**不必拆分**：
- 一个功能涉及多个文件
- 一个 bug 的修复改动多处
- 重构 A 时顺手调整了 A 的调用方

拆分建议输出格式（每组命令按 §1.2）：

    建议拆为 2 个 commit：

    # commit 1
    git add "src/http/http_client.hpp" "src/http/http_client.cpp"
    git commit -m "feat: 添加 HttpClient 同步 POST 封装"

    # commit 2
    git add "src/llm/llm_client.cpp"
    git commit -m "refactor: LLMClient 改用 HttpClient"

## 6. 本项目术语表

提交时优先使用下列模块名（与目录名一致）：

| 目录 / 文件 | 提交中的称呼 |
|-------------|--------------|
| `src/core/server.*` | Server |
| `src/core/session.*` | Session |
| `src/routing/router.*` | Router |
| `src/llm/chat_engine.*` | ChatEngine |
| `src/llm/chat_session_manager.*` | ChatSessionManager |
| `src/llm/llm_client.*` | LLMClient |
| `src/llm/chat_context.hpp` | ChatContext |
| `src/main.cpp` | 入口 / main |

外部库：
- Beast（不要写 `boost::beast` 全名，除非在正文）
- Asio（同理）
- nlohmann-json（或写 `nlohmann`）

## 7. 示例（diff → commit + 命令）

### 示例 1：新增文件

**diff**：新增 `src/http/http_client.hpp` 和 `src/http/http_client.cpp`，实现 `HttpClient::post()`。

**输出**：

    git add "src/http/http_client.hpp" "src/http/http_client.cpp"
    git commit -m "feat: 添加 HttpClient 同步 POST 封装"

### 示例 2：修 bug，根因不直观

**diff**：`session.cpp` 中 `path` 的赋值从 if 内部移到 if 之前。

**输出**：

    git add "src/core/session.cpp"
    git commit -m "fix: Session 空 target 导致 404" -m "handle_request 里 path 只在 target 含 ? 时赋值，导致所有不带 query 的请求全部走 404。改成先 path = target，再按 ? 拆 query。"

### 示例 3：重构 + 依赖变更，需拆分

**diff**：
- `vcpkg.json` 增加 `nlohmann-json`
- `llm_client.cpp` 改用 nlohmann-json 解析响应
- `main.cpp` 删除注释掉的示例代码

**输出**：

    建议拆为 3 个 commit：

    # commit 1
    git add "vcpkg.json"
    git commit -m "chore: vcpkg.json 添加 nlohmann-json 依赖"

    # commit 2
    git add "src/llm/llm_client.cpp"
    git commit -m "refactor: LLMClient 使用 nlohmann-json 解析响应"

    # commit 3
    git add "src/main.cpp"
    git commit -m "chore: 删除 main.cpp 中无用的示例注释"

### 示例 4：文档更新

**diff**：`docs/架构.md` 中移除 HttpParser 类。

**输出**：

    git add "docs/架构.md"
    git commit -m "docs: 架构图移除已删除的 HttpParser"

### 示例 5：多个模块混合，需拆分

**diff**：修改 `chat_engine.cpp`（接入 LLMClient）和 `session.cpp`（改超时）。

**输出**：

    建议拆为 2 个 commit：

    # commit 1
    git add "src/llm/chat_engine.cpp"
    git commit -m "refactor: ChatEngine::process 接入 LLMClient"

    # commit 2
    git add "src/core/session.cpp"
    git commit -m "fix: Session 读写超时调整为 30 秒"

## 8. 反例

| 反例 | 问题 |
|------|------|
| `更新` | 没信息 |
| `fix bug` | 没信息，且未指定模块 |
| `feat: 添加功能` | 什么功能？ |
| `修改 session.cpp 里的几行代码` | 复述 diff，没有意图 |
| `feat: 添加 HttpClient 并修复 Session 超时并更新文档` | 三件事塞一个 commit |
| 只给 message，不给 add/commit 命令 | 用户还得自己拼命令，易漏 add 文件 |
| `git add -A` + 单条 commit | 拆分场景下会串文件，且可能误提交无关改动 |
| `git commit -F- <<'EOF' ... EOF` | heredoc 是 bash 专有，PowerShell 报 `<` 保留错误 |
| 正文超过 2 句 / 60 字 | 在复述 diff，不是在解释动机 |

## 9. 让 AI 生成 commit 的操作步骤

**前提**：你手头有一批已 `git add` 或未暂存的改动。

**步骤**：

1. 终端跑，打印改动内容：

       git diff HEAD > diff.txt

2. 复制 diff.txt 输出。

3. 到 AI 对话里，粘这段话 + 第 2 步复制的内容：

   > 分析以下 git diff，按 `docs/提交规范.md` 生成 commit message 与提交命令。
   > 若需要拆分，先给拆分方案。
   >
   > ```
   > （粘贴第 2 步复制的内容）
   > ```

4. AI 返回 message 与可直接执行的 `git add` / `git commit` 命令。

5. 按顺序复制执行。单 commit 场景直接粘贴；拆分场景按 `# commit N` 分组逐组粘贴。

**想确认暂存区里有什么**：

    git status

**提交后核对**：

    git log -1 --stat
